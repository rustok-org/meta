## 1. Текущее состояние (что уже на `console/main`, PR #8)

- **`src/theme.rs`** — палитра по ролям из токенов сайта (`approve`/`high_risk`/`reject`/`frame`/
  `accent`/`ink`/`muted`), `NO_COLOR` через чистый `resolve()`-seam. Канон рамки `#2A1C4D`, акцент
  `#9D5CFF`, approve `#16E0C3`, high-risk `#FFB454`, reject `#FF6B6B`, ink `#EDE7FF`.
- **`src/format.rs`** — `wei_to_eth` (bignum-safe строковой математикой), `is_zero_wei`.
- **`src/ui.rs`** — все экраны framed (`themed_block`), карточка: человеческая сумма лидом,
  адреса **verbatim**, declutter, риск янтарём, Approve тил / Reject красный.
- Модель одобрения (`app.rs`), протокол (`protocol.rs`), транспорт (`transport.rs`) — НЕ тронуты.
- Консоль остаётся **one-shot approver**: `hello → auth → watch → approve/deny → exit`.

## 2. Целевой дизайн (полный) — резидентное приложение-кошелёк

Консоль перестаёт выходить по решению и становится **пультом**. Экраны (виды):

| Вид | Назначение | Данные | Статус |
|---|---|---|---|
| **Locked / Unlock** | PIN-вход | — | ✅ есть (тематизировать доп.) |
| **Dashboard** | баланс · позиции · «waiting for you» · активность | context + positions + activity | НОВОЕ (Фаза 2) |
| **Approve · send** | карточка одобрения перевода, два-блочный From→To | get + context(адрес отправителя) | карточка есть; From→To — Фаза 2 |
| **Approve · swap** | своп-карта (You pay → You receive, курс/слиппедж/route) | get + swap-декод | Фаза 2 (нужен core-декод) |
| **Approve · high-risk** | unlimited-approve: HIGH RISK + PIN (+ чекбокс?) | get | карточка есть; чекбокс — issue console#6 |
| **Receive** | адрес + QR | context(адрес) | НОВОЕ (Фаза 2, чистый дисплей) |
| **Activity / History** | список решений с фильтрами | локальный лог + retained outcomes | НОВОЕ (Фаза 2) |
| **Executing / Resolved** | «signing… / executed 0x… / FAILED» | resolve | есть (тематизировать) |
| **Send (manual)** | человек сам инициирует перевод | origination-op | КРУКС (см. §7) |

**Навигация:** вкладки/клавиши (`d` dashboard · `a` approve · `s` swap · `r` receive · `h` history ·
`l` lock · `q` quit), как в макете. Выделение — акцент. Мотион (бегущие стрелки From→To) —
**опционально** и только с явным счётчиком кадров (см. §6, в Фазе 1 убрана осознанно).

## 3. Архитектура и зависимости (критично — без этого дашборд не собрать)

**Инвариант №1 (нерушимый): консоль НЕ держит ключ шлюза.** Все данные идут через approver-сокет,
который отвечает `core` из своих данных. Прямой вызов gateway из консоли = ключ = граница A3 = ЗАПРЕЩЕНО.

**Расширение approver-протокола read-операциями** (core, приватный репо; `proto` +1, обратная
совместимость через `hello`). Ядро уже имеет данные (gateway-роуты `context`/`balance`/`positions`):

| Новая socket-op | Отдаёт | Источник в core |
|---|---|---|
| `context` | **адрес кошелька (signer)**, allowed_chains, балансы | `wallet_context` (gateway/lib.rs:97) |
| `positions` | Aave (collateral/debt/health/LTV), ERC-4626 (shares) | `positions` crate (`Protocol`, `Position`) |
| `activity` | последние терминальные исходы (executed/denied/expired/failed + tx_hash) | retained-outcomes store (60 мин) + локальный лог консоли для истории глубже |

**`context.address` разблокирует двух-блочный From→To** — сегодня адреса отправителя в протоколе нет,
это и была причина отложить From→To из Фазы 1.

`list`/`get` уже разрешены до `auth` (§2 протокола) — read-дашборд может показывать баланс до PIN?
**Решение к ратификации:** балансы/позиции показывать ТОЛЬКО после `auth` (баланс — приватная
инфа), в отличие от очереди (карточка не секрет). Внести в §2 протокола явно.

## 4. Инварианты безопасности (держать во ВСЕХ фазах — Ревьюер проверяет на каждом гейте)

1. **Адреса verbatim на любой подписывающей/одобряющей поверхности** (карточка, From→To, swap):
   НЕ сокращать — address-poisoning. Сокращение `format::short_addr` — ТОЛЬКО на дашборд-списках
   (activity), где это дисплей, не подпись. (В Фазе 1 `short_addr` убрана как dead-code — вернуть
   в Фазе 2 для дашборда.)
2. **Консоль не держит ключ шлюза** (§3).
3. **Правило двух окон:** у MCP/агента НЕТ пути к сокету (греп-инвариант приёмки mcp сохраняется);
   любая origination-op (ручной send) — **socket-only, агенту недостижима**.
4. **PIN на high-risk**, default-deny по дедлайну, exit-коды #7 — не ослаблять.
5. **`priority_fields_fit`-гейт** («нельзя одобрить нечитаемую карточку») — держать; новые
   элементы карточки идут в `priority_lines()`, гейт их считает.
6. **Никаких секретов на экране/в логах** (сид/keyring/PIN — не рендерить, PIN только точками).
7. **verbatim-отображение** значений ядра (`AGENTS.md` #1): re-basing для дисплея (wei→ETH) можно,
   ре-деривация/интерпретация — нельзя.

## 5. Фазы — конкретные deliverables

### Фаза 2 — Резидентный дашборд + read-слой (репо `console` + `core`)
**core (приватный):** socket read-ops `context`/`positions`/`activity` в `crates/grpc/src/approver.rs`
+ `APPROVER-PROTOCOL.md` (proto+1); тесты сериализации; матрица совместимости.
**console:**
- Модель: перестаёт выходить по решению — после `approve/deny` возврат на дашборд (правка
  `app.rs` — это **поведение**, отдельный аккуратный подкруг с переработкой тест-фикстур, как
  авто-открытие; замерить blast radius ДО).
- Виды: Dashboard (баланс/позиции/waiting/activity), Receive (адрес + QR — крейт `qrcode` или
  ASCII-QR ручной; проверить `cargo deny`), Activity, навигация-вкладки.
- **Двух-блочный From→To** на карточке (теперь есть `context.address`): блок «From: your wallet
  0x…(полный)» → стрелка → «To: 0x…(полный)»; строки внутри `priority_lines()`.
- Локальный лог активности (терминальные исходы переживают 60-мин retention ядра).
**Тесты:** снапшоты каждого вида + `.style().fg`-ассерты цвета (как в Фазе 1); read-ops
red→green; поведение «не выходим после решения» red-мутацией.

### Фаза 2.5 — Swap-карта (репо `core` + `uniswap` + `console`)
Core-декод свап-ордера: Universal Router calldata → tokenIn/out, amountIn/minOut, route, price-impact
(логика маршрута — репо `uniswap`); новое поле в `Card`/`get` (proto-аддитив). Console: swap-вид
(«You pay → You receive», курс/слиппедж/min-received/route, строка «approval: exact — not unlimited»).

### Фаза 3 — Демон + compose (репо `mcp`+`core`, арка §1.6)
Long-lived кошелёк-сервис; консоль переживает агентские сессии, подключается к демону (не `docker
exec`); compose-канал для контейнерных агентов; модель выдачи агентских токенов; healthcheck.
Отдельная спека/эпик.

### Бэклог (свои маленькие круги)
- **Авто-открытие единственного pending** — issue console#7 (поведение, ~30 тестов на `watching()`).
- **Чекбокс unlimited-approve** — issue console#6 (обещание спеки Этапа 3).
- **Сокращённые адреса на дашборде** (`short_addr` вернуть — ТОЛЬКО дисплей-списки).

## 6. Мотион (анимация From→To) — если возвращаем
В Фазе 1 убрана: `render(model, now_unix)` получает `now_unix` в СЕКУНДАХ, `Msg::Tick` раз в 2500ms —
для 250ms-марки нужен **счётчик кадров**, инкремент в `main.rs` на redraw, проброс в `render` (смена
сигнатуры → рябь на тестах), строка потока ВНУТРИ `priority_lines()` (иначе гейт её не считает,
регрессия читаемости). Тестировать детерминированно по счётчику + граничный снапшот. **Рекомендация:**
только если Капитан явно хочет; иначе статичный From→To достаточен.

## 7. Крукс — ручной Send / Receive (решить `/crucible` + ADR ДО постройки)
- **Receive** — безопасно, чистый дисплей (адрес + QR), кладётся в Фазу 2 без круксов.
- **Send вручную** — консоль становится **инициатором** транзакции, не только approver'ом. Нужна
  origination-op в сокете (не ключ шлюза — инвариант §4.2), и **обязательный инвариант: у агента/MCP
  нет пути к этой op** (человек может слать, агент — нет). Флоу: человек заполняет → core строит
  preview (socket-op) → карточка → человек подтверждает (PIN на high-risk) → sign+broadcast. Это
  эволюция модели «human-approved» → отдельный крукс+ADR, Фаза 2/3.

## 9. Открытые решения к ратификации (Гейт-1 соответствующих фаз)
1. Балансы/позиции — только после `auth` (рекомендую) или до (как `list`)?
2. Ручной Send — эволюция модели: делаем в Фазе 2, отдельным круксом (Receive — без крукса)?
3. QR для Receive — крейт `qrcode` (проверить лицензию/`cargo deny`) или ASCII-QR своими руками?
4. Мотион From→To — возвращаем со счётчиком кадров или статично (рекомендую статично)?
5. Порядок: Фаза 2 целиком, или сначала «резидентность + From→To» (нужен только `context`-op),
   потом позиции/activity/swap отдельными подкругами (рекомендую дробить — меньше blast radius).

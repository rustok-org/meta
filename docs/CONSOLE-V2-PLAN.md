# Console v2 — план реализации (терминальное приложение-кошелёк)

> **Статус:** ПРЕДЛОЖЕНИЕ, ждёт ратификации Капитана (Гейт-1). Кода нет до «go».
> **Дизайн-референс:** артефакт-макет (Dashboard / Approve / Swap / High-risk, палитра сайта,
> анимация потока) — https://claude.ai/code/artifact/9e435945-33c2-4f26-acad-d4c32bb3b176
> **Дата:** 2026-07-12 · автор: Инженер · по запросу Капитана «настоящее приложение в терминале».

## Видение

Консоль перестаёт быть одноразовым approver'ом и становится **пультом управления кошельком**:
человек остаётся в приложении, видит баланс, DeFi-позиции и историю решений, а одобрение
транзакции (send / swap / high-risk) — лишь одно из действий, поданное как **живой поток**
«откуда → куда». Ключи не покидают машину; агент только предлагает; это окно — человека.

## Инварианты безопасности (держим во ВСЕХ фазах)

1. **Консоль НЕ держит ключ шлюза.** Все данные (баланс/позиции/очередь) идут через
   approver-сокет, который отвечает core, — не через прямой gateway-вызов (иначе граница A3).
2. **Правило двух окон.** Консоль — окно человека; у MCP-слоя нет пути к сокету (греп-инвариант
   приёмки сохраняется).
3. **PIN на high-risk** и default-deny по дедлайну — как в v0.1, не ослабляем.
4. **Никаких секретов на экране/в логах** (сид/keyring-пароль через сокет не ходят — и не начнут).

## Фаза 2 — Резидентный дашборд (read-слой; `console` + `core`)

**Скоуп:** консоль перестаёт выходить по решению — живёт, показывает дашборд, поллит очередь.
- **PIN-unlock → Dashboard:** баланс (balances), DeFi-позиции (Aave health/LTV, ERC-4626),
  активность (последние executed/denied/expired/failed), «Waiting for you» (очередь).
- **Approve inline** из дашборда (клик/`a`), после решения **не выходим** — возврат на дашборд.
- **Локальный журнал активности** (терминальные исходы ядро держит 60 мин; для истории нужен
  свой локальный лог на data-dir).

**Что нужно от `core` (приватный репо):** расширить approver-протокол **read-операциями**
(`context` / `balances` / `positions` / `activity`), которые core отвечает из своих данных, —
консоль остаётся на сокете, ключ шлюза не трогает (инвариант #1). Обновить
`APPROVER-PROTOCOL.md` (proto-версия +1, обратная совместимость через `hello`).

**Репо:** `console` + `core` · **зависит от:** Фаза 1. **Даёт:** ровно то, что просил Капитан —
«оставаться в приложении, видеть баланс». **Оценка:** средний. **Риск:** протокол-версия (тесты
совместимости core↔console), не сломать существующую приёмку.

## Фаза 3 — Демон + compose (резидентный кошелёк; арка §1.6)

**Скоуп:** кошелёк как долгоживущий сервис-сосед; консоль **переживает агентские сессии** и
подключается к работающему демону; compose-канал для контейнерных агентов (дыра покрытия §1.6).
- Long-lived режим entrypoint; модель выдачи агентских токенов (не loopback-минт); healthcheck;
  compose-канон в доках; пересмотр остаточного MITM (Р3).
- Консоль переходит с `docker exec` на подключение к сервису (сокет по volume-mount или сети).

**Репо:** `mcp` + `core` + доки · **зависит от:** Фаза 2 + отдельная спека арки (§1.6 уже описана
в DISTRIBUTION-PLAN). **Даёт:** «приложение, которое всегда открыто» + установимость для агентов
в Docker. **Оценка:** большой, отдельный эпик со своими гейтами.

## Окно Uniswap — где живёт (спроектировано заранее)

Своп — **agent-proposed** (NORTH-STAR), значит это НЕ отдельная поверхность: агент предлагает
swap-транзакцию, она падает в ту же очередь одобрения, а консоль рендерит её **богатой
swap-карточкой** (вкладка Swap в макете). Место зарезервировано в Фазе 1 (look). Полный декод
свап-ордера (Universal Router calldata → tokenIn/out, amountIn/minOut, route, price-impact) —
**core-тикет**: сегодня карточный `decoded_call` покрывает approve/transfer/permit и т.п., но не
разбирает свап-роут. Логика маршрута свапа — репо `uniswap` (агентская сторона). Итог: место и
вид — Фаза 1; данные — core-декод + uniswap, отдельным тикетом, не блокируя редизайн.

## Решения к ратификации (Гейт-1)

   Согласен ли; или сразу целимся в резидентный дашборд (Фаза 2), приняв больший первый круг?
2. **Палитра/язык** — моно-везде + палитра сайта (как в макете) — ок как канон?
3. **Swap-данные сейчас или потом** — богатый декод свапа заводим отдельным core-тикетом
   (рекомендую) или тянем в Фазу 1?
4. **Дашборд-контент** — что выносим крупно: баланс · «waiting for you» · позиции? (влияет на layout).

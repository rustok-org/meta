# Карта идентичностей релиза — аудит 2026-08-04

Что чем называется в rustok, кто это держит, и где сегодня расходится.

Повод: во время выпуска круга «гейт возможностей на пути» выяснилось, что точек версии
заметно больше, чем знал план, и что часть из них не стережёт ничто. Дважды за месяц линии
ломались на «версию бампнули — пины не бампнули»; этот документ существует, чтобы третьего
раза не было.

Всё ниже проверено запросами и чтением файлов 4 августа 2026, не по памяти.

---

## 1. Четыре разных «версии», которые легко перепутать

| Идентичность | Что это | Кто выставляет | Пример |
|---|---|---|---|
| **Версия пакета** | `pyproject.toml` / `Cargo.toml` | коммит | `0.8.3` |
| **Тег образа** | метка в GHCR | пуш образа | `rustok-wallet-tui:v0.8.3` |
| **Git-тег** | точка в истории | `git tag` | `wallet-tui-v0.8.3`, `v0.1.5` |
| **Дайджест** | сами байты | реестр, после публикации | `sha256:951fc20d…` |

Путать их дорого: **дайджест не существует до публикации**, поэтому пин ставится отдельным
коммитом ПОСЛЕ; **git-тег указывает на коммит**, поэтому он ставится последним, когда пин уже
внутри.

## 2. Сломано прямо сейчас

### 2.1 ✅ ЗАКРЫТО — не было git-тегов на уже выпущенное

Образ `rustok-wallet` 0.4.5 опубликован, скилл 0.5.0 залит на ClawHub — а тегов нет:

```
wallet-v0.4.5   ❌ отсутствует   (конвенция: wallet-v0.4.4, v0.4.3, v0.4.2 … есть)
skill-v0.5.0    ❌ отсутствует   (конвенция: skill-v0.4.9, v0.4.8, v0.4.7 … есть)
```

**Чем плохо:** история линии теряет точку, в которой собрался опубликованный образ. Через
месяц «из чего собран `v0.4.5`» станет археологией по датам коммитов.

**Починено 2026-08-04:** оба тега поставлены на `1fd1e91` (`chore(release): 0.4.5`),
аннотированные, с дайджестом опубликованного образа в тексте тега.

**Почему это было безопасно сделать без отдельного разрешения — проверено, не предположено:**
в `mcp` на пуш тега реагируют `docker-publish.yml` и `ci.yml`, оба по шаблону `tags: ['v*']`.
Продуктовые пространства (`wallet-v*`, `skill-v*`, `wallet-tui-v*`) под него **не подпадают** —
они начинаются не с `v`. То есть эти теги полностью инертны: пометка истории, ноль сборок.
Пространство `v*` в `mcp` принадлежит старому питон-пакету `rustok-mcp`, и именно поэтому
продуктовые теги живут вне его.

### 2.2 🔴 `server.json` агентской линии врёт сам себе

```json
"version": "0.4.4",
"identifier": "ghcr.io/rustok-org/rustok-wallet:v0.4.2"
```

Версия отстала на один выпуск, **образ — на три** (v0.4.2 от 31 июля). Внутри одного файла
два разных ответа на «какая это версия».

Это манифест **MCP Registry** — не ClawHub, отдельная витрина. Консольный `server.json`
согласован (`0.8.3` / `v0.8.3`), агентский разъехался и **не был замечен три выпуска подряд**.

**Причина, по которой не заметили:** ни один тест не смотрит внутрь `server.json`.
`test_claw_manifest.py` проверяет только, что `claw.json` — не копия `server.json`.

### 2.3 🟡 Лёгкие теги вперемешку с аннотированными

Без аннотации: `skill-v0.4.7`, `skill-v0.4.8`, `skill-v0.4.9`, `wallet-tui-v0.6.0`,
`wallet-tui-v0.8.0`, `wallet-v0.4.3`, `core: v0.1.3`.

Лёгкий тег не несёт ни автора, ни даты, ни сообщения — `git for-each-ref` по ним отдаёт тему
коммита, а не описание релиза. Задним числом не чинится (перевесить = переписать тег), но
дальше ставить только аннотированные.

### 2.4 🟡 Легаси-теги `v0.1.0` и `v0.1.2` в `mcp`

Июнь 2026, до разделения имён. Сейчас в `mcp` живут три осмысленных пространства
(`wallet-*`, `wallet-tui-*`, `skill-*`) плюс эти два сироты из времён, когда репозиторий был
одним питон-пакетом. Комментарий в `tests/test_docs_one_command.py:42` про них помнит и
явно запрещает переиспользовать это пространство.

**Не удалять** — на них могли ссылаться. Просто знать, что это не текущая схема.

### 2.5 🔴 Страж пинов шима в CI не работает — и не может

`tests/test_installer_pins.py::test_the_pinned_shim_is_the_shim_in_this_tree` сверяет
`cli/rustok` в дереве с тем, что лежит в коммите `SHIM_COMMIT`. Поставлен 2026-08-04 со
словами «забыть станет невозможно».

**Замерено на настоящем неглубоком клоне:** `actions/checkout` берёт `fetch-depth: 1`,
пинованный объект не читается, тест уходит в `pytest.skip`. То есть в единственном месте, где
он запускается автоматически, он не запускается **никогда**. Локально — работает.

**И это не просто недосмотр с глубиной клона.** Страж по устройству не может быть зелёным во
время процесса, который сторожит: `SHIM_COMMIT` обязан называть **уже существующий** коммит с
новым шимом, значит между «поменяли шим» и «перепиновали» всегда есть красное состояние.
Включить `fetch-depth: 0` — значит сделать красным коммит, без которого релиз не едет.

**Что с этим делать — отдельным кругом, не в релизный день.** Варианты, ни один пока не
выбран: (а) страж строг только на релизном теге, а не на каждом коммите; (б) страж требует не
«пин совпадает», а «пин совпадает ИЛИ следующий коммит его чинит» — тогда нужен способ это
выразить; (в) шим перестаёт нести версию образа, и тогда его вообще незачем перепиновывать
каждый выпуск. Вариант (в) выглядит самым честным: `DEFAULT_IMAGE` в шиме — единственная
причина, по которой шим меняется каждый релиз.

**Урок шире одного теста:** страж, который не может быть зелёным в нормальном ходе работы,
будет либо отключён, либо начнёт блокировать работу. Мой выбрал молчать — и молчал ровно там,
где был нужен.

## 3. Пространства git-тегов

| Пространство | Линия | Что помечает |
|---|---|---|
| `v0.1.x` в `core` | агентская | замороженная линия ядра |
| `v0.2.x`, `v0.3.x` в `core` | консольная | активная линия ядра |
| `wallet-v0.4.x` в `mcp` | агентская | выпуск образа кошелька |
| `skill-v0.4.x` / `v0.5.0` в `mcp` | агентская | выпуск скилла на ClawHub |
| `wallet-tui-v0.8.x` в `mcp` | консольная | выпуск образа **и** скилла сразу |

**Почему у агента два пространства, а у консоли одно.** На агентской линии версия скилла и
версия пакета разъединены по замыслу (скилл 0.5.0 при пакете 0.4.5), поэтому у скилла свой
тег. На консольной они связаны тестом `test_every_version_point_matches_the_manifest`, поэтому
хватает одного. Это **осознанное** расхождение, не небрежность.

**Особая роль `wallet-tui-vX.Y.Z`:** это не только метка истории. По нему тянется установщик:

```
https://raw.githubusercontent.com/rustok-org/mcp/wallet-tui-v0.8.3/scripts/install.sh
```

То есть **тег обязан существовать до того, как витрина начнёт на него ссылаться**, иначе
команда установки отдаёт 404 всем. И наоборот: не обновишь ссылку — люди качают старый
установщик, а он пинит старый дайджест, то есть предыдущий образ.

## 5. Состояние GHCR на 2026-08-04

```
rustok-core       v0.1.5, v0.1 → 1aadb2ac    v0.1.4 → 6dbed391
rustok-wallet     v0.4.5, v0.4, v0, latest → 62676b9e    v0.4.4 → e4804fac
rustok-wallet-tui v0.8.3, v0.8, v0 → 951fc20d       (без latest — так и задумано)
```

- `rustok-wallet-tui` **сознательно без `latest`**: `flavor: latest=false` в
  `wallet-publish.yml`, потому что установщик тянет по дайджесту, а не по метке.
- Записи с тегом вида `sha256-951fc20d…` — это подписи cosign, не мусор.
- Записи без тегов (`[]`) — служебные манифесты, трогать не надо.
- `rustok-core` публикует **две** метки с замороженной линии (`v0.1.5`, `v0.1`) и **не
  трогает** `v0`/`latest`: они принадлежат активной линии. Это записано комментарием прямо в
  `docker-publish.yml` и является правильным поведением.

## 6. Настоящий порядок выпуска

### Консоль — **три коммита**, а не два

```
1. коммит A: версия ядра → PR → мерж → git tag vX.Y.Z ядра → CI публикует образ ядра
2. коммит B: ARG CORE_IMAGE + ВСЕ точки версии кошелька (см. §4) → PR → мерж
3. workflow_dispatch wallet-publish.yml, ОБЯЗАТЕЛЬНО с ветки main → образ + cosign
4. коммит C: WALLET_DIGEST (появился только сейчас) + SHIM_COMMIT → PR → мерж
5. git tag wallet-tui-vX.Y.Z на коммит C  ← ссылки установщика ведут СЮДА
6. заливка claw.json на ClawHub
```

Шаг 5 обязан идти после шага 4: тег указывает на коммит, и по нему качают `install.sh`. Если
поставить тег на коммит B, установщик по этой ссылке будет пинить **прошлый** дайджест.

**Почему `с ветки main`:** `install.sh:49` пинит
`…/wallet-publish.yml@refs/heads/main` буквально. Диспатч с другой ветки даёт подпись, которую
`cosign verify` не примет — сломается проверка у всех сразу.

**Неустранимое окно** между шагами 2 и 3: guard в самом workflow требует, чтобы
`inputs.version` равнялся `pyproject.toml`, значит манифест бампается строго до диспатча. В
это окно `pyproject` говорит новое, а живые байты старое. Установщик тянет по дайджесту, а не
по строке версии — окно даёт кривую подпись в выводе, не кривые байты.

### Агент — два коммита + ручная публикация

```
1. версия ядра → тег → CI публикует ядро
2. ARG CORE_IMAGE + пакет + скилл + CHANGELOG → PR → мерж
3. сборка + ручной пуш ЧЕТЫРЬМЯ тегами (vX.Y.Z, vX.Y, vX, latest)
4. git tag wallet-vX.Y.Z и skill-vA.B.C
5. заливка claw.json на ClawHub
```

Автоматизировать шаг 3 сегодня нельзя: `wallet-publish.yml` этой линии собирает
`CORE_IMAGE=…rustok-core:${{ github.ref_name }}` (на диспатче с ветки это имя ветки, `FROM` не
разрешится), не имеет `inputs.version` и `value=` у `type=semver`, и **не содержит cosign
вовсе**. Это переписывание по образцу консольного, отдельной задачей.
